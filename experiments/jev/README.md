# Offline Jev candidate-choice experiment

This is the next step after the Classic corpus: ask Jev to select one candidate
from an existing recorded decision. It does not modify SVGnest or run Jev in the
browser worker. It does not yet replay changed choices or measure Jev utilisation.

## Prepare the exact requests without a key

From the repository folder, on `experiment/jev-placement-policy`:

```powershell
git pull --ff-only
npm.cmd ci
npm.cmd run jev:prepare
```

Use `npm` outside Windows. This loads the bundled baseline ZIP directly: no manual
extraction or new browser run is needed. The default is 20 decisions, selected in
round-robin order across the ten best Classic evaluation snapshots. No network
calls occur in preparation mode, even if an API key is configured.

Outputs go into a timestamped `jev-results/` directory. Inspect `requests.ndjson`
to see the source identity, request hash, Classic comparison label and exact API
payload. **Only each record's `request` object is sent to Jev.** The comparison
label and snapshot provenance stay local.

## Make the real API calls

Get a key from the [TypeSafe console](https://console.typesafe.ai). Enter it locally
at a masked prompt in PowerShell; it does not need to be pasted into chat or saved
in the repository:

```powershell
$jevSecret = Read-Host "TypeSafe API key" -AsSecureString
$env:TYPESAFE_API_KEY = [System.Net.NetworkCredential]::new("", $jevSecret).Password
npm.cmd run jev:evaluate -- --limit 20
Remove-Item Env:TYPESAFE_API_KEY
$jevSecret.Dispose()
```

The command makes at most one initial request for each selected decision, with up
to two retries for HTTP 429/529. Successful decisions are appended as they finish.
A malformed response, unsupported request or API failure stops the run. There is
no silent Classic fallback and no automatic retry of uncertain network/timeouts.
Repeating a live command makes new calls; there is no response cache or resume
mechanism in this initial evaluator.

For a larger sample or your own captured run:

```powershell
npm.cmd run jev:prepare -- --limit 100
npm.cmd run jev:evaluate -- --input benchmark-results/YOUR-RUN --limit 100
```

Inputs can be a baseline ZIP, a run directory, a `best-decisions.json` snapshot, or
`decisions.ndjson` from the corpus runner. ZIPs/directories select best evaluations;
NDJSON selects from all supplied evaluations. This distinction affects sampling
and agreement statistics. Supply `--out DIRECTORY` to name the output folder; an
existing nonempty folder is rejected.

## Request and model contract

The adapter uses the documented HTTP endpoint with a single `choice` question,
Bearer authentication and `TYPESAFE_API_KEY`. It defaults to the pinned
`jev-1.13.0` model; override with `--model ID` when intentionally testing another
version. Returned model IDs are recorded. References checked 17 September 2026:
[API](https://docs.typesafe.ai/api), [Choice](https://docs.typesafe.ai/primitives/choice),
[models](https://docs.typesafe.ai/models).

Every option is a candidate ID already generated by SVGnest. No candidates are
pruned or relabelled. Decisions with fewer than two options need no model judgment
and are skipped. More than 255 options is rejected, matching the documented
Choice limit. The adapter also imposes a conservative 16 KiB request-body cap;
this is a local byte bound, not an exact service token calculation. The entire
selected batch is prepared before any API call, so unsupported inputs fail early.

The input includes current bounds, placed/remaining part summaries, original
candidate features and ranks computed in code. It excludes Classic's winner,
selection flags, future placements and final fitness. Compactness/growth ranks
are descriptive features, not labels of an optimal answer. No outline, cavity or
contact geometry is supplied in this initial experiment.

TypeSafe's [known limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13)
explicitly caution against relying on numerical precision. The adapter therefore
computes arithmetic and ranks locally. Whether the remaining feature-based
judgment helps packing is an unproven hypothesis. More numeric detail by itself
should not be assumed to improve Jev's spatial judgment.

## Results and their limits

- `metadata.json`: mode, model, endpoint, source hashes, selection policy and counts.
- `requests.ndjson`: exact payloads and separate local Classic comparison labels.
- `choices.ndjson` (live only): validated candidate IDs, probabilities, confidence,
  reported model, usage, observed latency, agreement and local bounding changes.
- `summary.json`: prepared counts in dry mode; agreement, request attempts, tokens
  and latency in live mode. `finalUtilisation` is explicitly null.
- `error.json`: live-run failure and the number of completed decisions, if any.

A model disagreeing with Classic is not evidence of improvement. A lower local
bounding score is not evidence of improved final utilisation. Confidence measures
model certainty, not a validated probability of producing the best final nest.

After a successful live run, the next implementation is **geometry replay**:
apply the chosen candidate, regenerate the subsequent legal region/candidates,
and continue from that changed state with identical input/order/rotation budgets.
Do not chain later candidate IDs from the original Classic snapshot once a choice
has changed. Finish by validating the layout and comparing final bins, utilisation,
unplaced parts and runtime against Classic.

## Checks

```powershell
npm.cmd run test:jev
```

These tests use real saved snapshots and a mocked HTTP transport. They check the
request schema, label exclusion, every candidate option, numerical ranks, response
validation, retry behavior and no-key dry run. They do **not** test the live service
or demonstrate a Jev nesting improvement.
